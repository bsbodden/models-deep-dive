# Why do we need Rust?

## Start with the performance we require

Models evaluates performance at the application boundary: how long a user waits for the first token, how quickly the remaining tokens arrive, and how long the complete request takes. Our thresholds distinguish a model that runs correctly from one that feels responsive on the tested hardware.

For standalone text generation, the benchmark uses these limits. **TTFT** is time to first token; **TPOT** is time per output token after generation starts. **p95** is the 95th percentile, so these limits account for slower trials rather than just the average.

| Generation tier | p95 TTFT | p95 TPOT |
| --- | --- | --- |
| Interactive | At most 500 ms | At most 40 ms |
| Responsive | At most 1 second | At most 100 ms |
| Usable | At most 2 seconds | At most 200 ms |
| Offline | Above 2 seconds, or TPOT above 200 ms | Either limit is exceeded |

Classification requires at least ten trials and every trial to succeed. The separate decode-throughput comparison labels at least 80% of the same artifact's llama.cpp throughput **competitive**, at least 50% **viable**, and anything lower **needs optimization**. These are the standalone benchmark's classifications, not the catalog admission rules. [Implementation](../../projects/models/models-bench/src/main/java/com/integrallis/models/bench/BenchmarkPolicy.java).

For retrieval-augmented generation, the complete pipeline has a separate set of limits:

| RAG metric | Production-ready tier | Usable tier |
| --- | --- | --- |
| p95 retrieval latency | At most 100 ms | At most 250 ms |
| p95 time to first token | At most 1 second | At most 2 seconds |
| p95 time per output token | At most 100 ms | At most 200 ms |
| p95 end-to-end latency | At most 5 seconds | At most 10 seconds |

All four limits must pass for the corresponding tier. A correct pipeline that exceeds the usable limits receives **performance-reduced** status. Qualification also requires quality: retrieval recall of at least 95%; reciprocal rank, fact coverage, citation recall, citation precision, and answer correctness of at least 90%; and correct abstention on every applicable case. The model itself must contribute answers on at least one-third of attempts, with at least 90% of those answers correct. An extractive fallback cannot substitute for that model contribution. [RAG tiers](../../projects/models/models-rag-bench/src/main/java/com/integrallis/models/rag/RagPerformancePolicy.java), [qualification policy](../../projects/models/models-rag-bench/src/main/java/com/integrallis/models/rag/RagProductionQualificationPolicy.java).

RAG qualification additionally compares the same model artifact on the same host under matching prompts, context, threads, and generation settings. Against the authoritative Ollama or Transformers baseline, Models must deliver **at least 80% of median decode throughput** and take **no more than 1.5 times the p95 end-to-end latency**. A reviewed, artifact-specific publisher reference uses those same limits. The ordinary llama.cpp comparison has a 45% throughput floor and a 2-times latency ceiling, but passing that comparison alone cannot qualify a model under the standard policy. A performance-reduced model can still qualify if it passes the quality, contribution, and relative gates; its slower absolute tier remains visible. [Comparison and admission logic](../../projects/models/models-rag-bench/src/main/java/com/integrallis/models/rag/RagProductionQualificationPolicy.java).

These admission thresholds do **not** authorize a regression when replacing an existing implementation. Shim retirement requires comparing the Java candidate directly with the retained native route and preserving the affected model's behavior and performance. The policies above do not define one universal percentage allowance for retirement, or universal numeric limits for memory, startup, allocation, or prefill throughput. Those need explicit, workload-specific criteria before an experiment. Relative TTFT is recorded but is not a separate relative qualification gate; absolute TTFT still determines the latency tier. [Relative metric semantics](../../projects/models/models-rag-bench/src/main/java/com/integrallis/models/rag/RagComparatorAssessment.java).

## How the Rust shims work

Models runs inference in Java, either using Java alone or with optional Rust shims that accelerate selected calculations while Java handles the rest. Java owns model loading, tokenization, the computation graph, model state, sampling, and generation. The CPU shims implement numerical operations that Java calls through the Foreign Function and Memory API. The native module packages platform-specific binaries whose identity, integrity, and binary interface are checked before loading. [Java integration](../../projects/models/backend-native/src/main/java/com/integrallis/models/backend/nativekernel/RustFfmBackend.java), [native calls](../../projects/models/backend-native/src/main/java/com/integrallis/models/backend/nativekernel/NativeKernelLibrary.java).

The GPU module contains Rust kernels compiled to PTX, NVIDIA's device instruction representation. Java loads and launches that code through the NVIDIA driver and manages device resources. This is a different execution target from the CPU Vector API. Apple's Foundation Models integration is separate: its Swift bridge calls Apple's system-managed model. [CUDA module](../../projects/models/backend-cuda/README.md), [Apple integration](../../projects/models/models-backend-apple/README.md).

## What the evidence establishes

We have measured benefits from particular Rust implementations on particular workloads. We also have compiler experiments showing differences in the instructions generated from Java. Those are related findings, but a faster Rust result alone does not establish that a JVM limitation requires the shim. Scheduling, memory layout, the algorithm, and the Java implementation can all affect the comparison.

The results below are retained experiments, not fresh measurements of every supported runtime. Their linked reports identify the tested artifacts, hardware, source revisions, and settings. **Known** describes implementation facts or those recorded results. **Unresolved** identifies what has not been demonstrated. Removal conditions are acceptance tests, not predictions that a particular JDK release will solve the problem.

Several historical reports call a control “published” because it uses published Vectors arithmetic. That control holds Models code separately; it is **not the complete released Models distribution**. Those measurements isolate changes within their recorded compositions. A release comparison additionally needs the actual downloadable Models artifacts, their declared dependencies and their bundled native binaries. That separate comparison has now completed for the smaller Qwen model: ARM passes its quality comparison, while x86 loses one JEVBench case. No historical result below substitutes for that comparison.

## Current qualification status

The final tested ARM composition preserves the historical published-core control's task scores for all three measured causal models: the smaller Qwen model, the larger Qwen model, and the Q5_1 model. Bonsai also passes all 200 paired public quality cases. Those quality results do not close the remaining resource gates. The final Bonsai screen passes every declared latency gate on both architectures, while several allocation, loading, and resident-memory confidence intervals remain unresolved. The x86 smaller-Qwen comparison still regresses on JEVBench: 75 correct cases against the actual released distribution's 76, with SNIPS improving from 14 to 15. ARM improves from 74 to 75 JEVBench cases and ties on SNIPS. The candidate passes the separate state checks on both architectures. Earlier comparisons against held Models and published-core arithmetic remain distinct experiments. Release remains blocked. [Current audit and exact runtime identities](../../library-audit-2026-10-12.md), [Bonsai quality](../../audit-artifacts/final-public-qa-fast-v3/RESULTS.md), [Bonsai resource results](../../audit-artifacts/bonsai-prepared-sleef-final-v1/RESULTS.md).

Two subsequent x86 candidates also fail the unchanged task-quality gate. A permissively licensed AMD exponential translation matches its assembly reference but scores 73/120 on JEVBench against its paired released control's 76/120. Retaining the recurrent state in double precision passes independent numerical and state-lifecycle checks but scores 70/120 against its paired released control's 77/120. In the latter run, the current Java and Rust FP32 recurrences both score 75/120 and produce identical owned outputs across all 148 requests. These are separate same-host comparisons, not pooled scores. Neither candidate is adopted. More precise recurrence arithmetic does not, by itself, preserve this model's task quality. [AMD comparison](../../audit-artifacts/aocl-x86-model-quality-v1/root-full-quality-verification.json), [FP64 comparison](../../audit-artifacts/qwen-fp64-state-v1/root-full-quality-verification.json).

The original Bonsai regression test requires exact full-vocabulary agreement between sequential and batched execution on the same host. That is a model-level contract. The released Vectors SwiGLU API specifies the activation formula and tests bounded numerical accuracy; it does not promise bit-for-bit StrictMath output or identity across hosts. The StrictMath-specific golden introduced during this work is an implementation choice, not an independent reason to keep a slower replacement. A narrowly controlled test is checking whether the published Java SwiGLU can meet the original model requirement while the other repairs remain fixed. Native calls must be explicitly declined and observed in that test, because an enabled Rust implementation can otherwise bypass the Java operation entirely. [Original requirements and limitations](../../audit-artifacts/published-swiglu-only-ablation-v1/REQUIREMENT-PROVENANCE.md), [actual operation routing](../../audit-artifacts/qwen-actual-release-operation-inventory-v1/RESULTS.md).

The sections below retain earlier experiments to explain the engineering decisions. Their source and runtime identities matter: a failure in an earlier composition is not automatically a failure in the current composition, and a later improvement does not erase the original result.

### Q4_0, Q5_0, and Q8_0 projections

**Known:** Java and Rust both implement these packed-weight matrix operations. Rust uses architecture-specific arithmetic; Java expresses its kernels through the Vector API. A retained compiler experiment found packed multiply-add instructions in the tested Graal output that the tested HotSpot compiler did not emit. However, the complete Q8 candidate using those instructions was slower than the established Java kernel on both runtimes. A separate Java Q4 formulation improved whole-model performance under its tested Graal configuration. Java alternatives have been implemented and measured, with both successes and rejected candidates. [Compiler experiment](../../projects/vectors/vectors-bench/jmh-results/vector-api-pairwise-jvm-baseline.md), [Java Q4 experiment](../../projects/vectors/vectors-bench/jmh-results/graal-q4-short-pairwise.md).

**Unresolved:** these results establish specific compiler behavior, not a universal reason to require Rust for all three formats. The Soprano investigation identifies Java Q8 projections as a bottleneck and retains a qualified Rust-assisted Q8 path, but its BF16 result uses different weights and is not a controlled Java-versus-Rust comparison. Each format still needs a current, matched comparison and a demonstrated cause for any remaining gap. [Soprano evidence](../../projects/models/benchmark-results/audio/soprano-1.1-80m-java/README.md).

A current Q5_0 investigation found another repairable Java defect: requesting 256-bit integer vectors on a 128-bit ARM host caused extreme allocation. A primitive integer implementation preserves the required arithmetic and eliminates that fallback. The full comparison against this repaired Java route gives Rust about 5.3 times lower request latency on ARM and six times lower on the tested x86 hosts. ARM retains all 148 cases' full logit snapshots exactly; x86 has identical JEVBench scores and one additional correct SNIPS answer with Rust. However, the complete resource gate has not passed: allocation varies between x86 processes, several intervals miss the precision requirement, and unequal classpaths confound the observed native startup increase. These are measured implementation differences, not proof of an unavoidable JVM limitation. The Java repair remains outside the release tree until its remaining checks are resolved. [Repair and full-model comparison](../../audit-artifacts/q50-model-qualification-v1/RESULTS.md).

**Removal condition:** a Java route preserves the numerical and task-quality contracts and meets the affected workload's performance and resource requirements against the retained Rust route. A faster isolated instruction is insufficient.

### Q4_K, Q5_K, and Q6_K projections

**Known:** these formats combine packed weights with block scales and, in some cases, minimum corrections. Both implementations handle that arithmetic; compatible native groups share activation preparation. A retained Qwen qualification used Rust projections and Java attention, delivering 29.45 tokens/second against Ollama's 33.53 on the recorded host. That establishes the tested configuration's result against an external comparator. It does not isolate Rust's gain over Java. [Qualification](../../projects/models/benchmark-results/certified-20260830/rag/qwen2.5-3b-instruct-q4_k_m/README.md), [Rust implementation](../../projects/models/backend-native/src/main/rust/model-kernels/src/lib.rs).

**Unresolved:** unpacking, scale handling, integer accumulation, register use, and mapped-memory access are candidates for investigation. The qualification alone does not identify which cost is a JVM limitation, or prove that the same explanation applies to every K-quant format.

**Removal condition:** qualify Java replacements separately for each affected format and configuration, including mixed groups, single-token decode, and batched prefill.

### Q5_1 projections

**Known:** the Rust kernel preserves Java's floating-point accumulation contract, including operations that must remain unfused. The earlier short embedding comparison did not exercise Rust: both arms loaded the Java engine, and BERT did not route its projections through the supplied kernel provider. That comparison cannot establish a native speedup. A corrected experimental integration explicitly routed BERT projections through Rust, counted the native calls, and compared 82 real query/document embeddings from SciFact and NFCorpus on x86 and ARM; their output vectors matched Java exactly. [Correction to the historical evidence](../../projects/models/benchmark-results/2026-10-08-q5-1-rust-shim/NOTES.md).

**What the investigation changed:** Java can unpack Q5_1 blocks with the Vector API, decode each weight row once for a batch, and share rows across the existing worker pool. These are implementation improvements, not missing JVM features. Actual BERT comparisons found lower latency with SIMD unpacking and parallel rows, but higher peak resident memory. Sharing the decoder fixed a separate per-row object allocation; it did not fix peak memory. Controlled comparisons then isolated scalar/SIMD decoding and serial/parallel rows. BERT now uses scalar, serial Q5_1 projections with a reused row buffer; the faster experiments did not clear the resource requirement. All 82 real embeddings match exactly on both hosts. Ten paired process comparisons show substantially lower allocation and peak-memory point estimates close to the prior route, but their confidence intervals do not establish the strict memory and startup gates. Causal models retain their separate projection path. [Final BERT measurements](../../projects/models/benchmark-results/2026-10-12-bert-restored-final/README.md).

**Earlier measurements:** no JVM limitation has been demonstrated for Q5_1. A separate causal-model comparison retained all 148 requests' nine full-logit snapshots exactly. Rust was faster for x86 decode, but slower for prefill on both hosts and for ARM decode. Therefore, a blanket native route is not justified. That follow-up narrowed native eligibility to x86 single-token projections; later measurements below evaluate a revised reuse kernel on both hosts. The precise boundary is an implementation and measurement result, not a claim that Java cannot perform the operation. The final scratch-allocation comparison completed ten paired processes per host with exact outputs and lower allocation, but ARM prefill, whole-request latency and resident memory regressed. That implementation has not passed qualification. [Final scratch comparison](../../projects/models/benchmark-results/2026-10-12-q51-scratch-final/README.md).

A subsequent ARM investigation found a separate implementation defect: the Java path requested 256-bit vectors on a host that executes 128-bit vectors. A model recording attributed nearly all sampled allocation to the resulting reduction and Q5_1 decoder fallbacks. Java can preserve the same eight logical reduction lanes using two native 128-bit vectors; the decoder can likewise process four weights per vector. On the tested ARM host, the corrected components eliminate warmed allocation and run about 27–77 times faster than those fallback implementations. All 148 model correctness cases pass with the corrected widths; whole-model performance and route selection remain under evaluation. These component gains cannot be read as equivalent whole-model speedups. This is evidence of a repairable Java implementation error, not a reason to require Rust. [Native-width finding and validation limits](../../projects/models-final-integration/docs/findings/q51-native-width-regression-2026-10-13.md).

A later comparison tested the revised native reuse kernel against that retained BERT route. Both hosts produced exactly the same 82 embeddings, and native calls were observed. Warm embedding latency improved, but loading became about 39% slower on ARM and 41% slower on x86. That tradeoff fails the startup requirement, so BERT keeps Java. This is a measured reason to reject that route change, not a JVM limitation. [Complete comparison](https://github.com/integrallis/models/actions/runs/38360868649).

An earlier composed causal-model comparison evaluates native row reuse against both the retained hybrid route and the historical published-core control. All 148 requests retain identical Java/native logit snapshots, and all three arms have the same task scores. Native reuse reduces whole-request time against the hybrid by about 14% on x86 and 20% on ARM. However, the complete candidate still allocates about 98% more on the first request than published on x86 and 18% more on ARM; peak resident memory also increases on both hosts. These results preserve the measured kernel improvement but block releasing the complete runtime. They do not identify the kernel as the cause of the remaining overhead. [Completed comparison and confidence intervals](../../audit-artifacts/2026-10-13-activation/q51-composed-final-38363772817/STATUS.md).

The completed follow-up repairs a missing native SwiGLU call in the ordinary Qwen graph. All candidate/hybrid/held snapshots remain exact and task scores match across all four arms. ARM request latency and allocation improve substantially against the historical published-core control; x86 loading still regresses, and other resource intervals remain unresolved. The complete result supersedes partial first-process observations. [Caller repair comparison](../../audit-artifacts/q51-llama-swiglu-route-v1/RESULTS.md).

An earlier completed causal-model screen retains exact candidate/hybrid/held outputs across all twelve original quartets on each host. Against the historical published-core control, ARM decode takes about 53% as long, but its peak resident memory is about 1.39% higher. x86 decode is about 0.88% slower. Both regression confidence intervals exclude parity. Faster complete requests do not cancel either failure, and the memory difference has not yet been attributed to a particular operation. This composition remains unqualified. [Complete result](../../audit-artifacts/q51-next-cleanup-screen-v2/github-38457335722/RESULTS.md).

The final ARM composition matches all 148 published task outcomes. Against published, request time is about 16% and decode time about 53% of baseline; those latency gates pass. Loading, warm allocation, cold allocation, and resident-memory precision remain unresolved, despite favorable point estimates. This later result supersedes the earlier ARM memory-regression verdict for the tested final composition; it does not qualify the unresolved metrics or the x86 composition. [Final ARM resource analysis](../../audit-artifacts/sleef-models-arm-v1/resource-analysis-v2/RESULTS.md).

**Removal condition:** select the Java or Rust implementation that preserves the numerical and task-quality contracts and passes the declared whole-model latency, startup, allocation, and memory requirements on the target hardware. An isolated speedup or an unproven compiler explanation is insufficient.

### BF16 projections and SwiGLU candidates

**Known:** both operations have Java implementations. The external native candidate targets the measured Bonsai BF16 matrix shape and uses the same declared arithmetic as the corrected Java route. Disabling only native BF16, while retaining native SwiGLU and all other kernels, increases first-request Java allocation in every fixed pair: about 1.75–2.03 times on x86 and 1.64–1.71 times on ARM. Full logit snapshots and generated tokens remain identical, and counters verify that the disabled operation did not execute. This is evidence of a contribution within that candidate, not a pure-Java-versus-Rust whole-model comparison. The counter begins after model loading. [Completed ablation and scope](../../audit-artifacts/bonsai-spi-ablation-v1/READOUT.md).

**What has been repaired:** a profile identified an escaping Java vector object in a reduction helper. Inlining its unchanged lane fold removes about 18 MB from a local warm Bonsai request without changing any captured logits. The subsequent eight-host composed comparison passes x86 warm allocation and ARM decode, but x86 decode is about 0.36% slower, with the entire confidence interval above parity. Loading, resident memory and some precision gates remain unresolved. Its comparator retains the same Models base and uses the published Vectors artifact; it is not the complete published runtime. The candidate remains unqualified. [Complete comparison](../../audit-artifacts/bonsai-source-repair-screen-v3/github-38454874690/RESULTS.md), [Java allocation repair](../../audit-artifacts/pinned-reduction-inline-fold-v1/actual-bonsai/summary.json).

Native linkage also has setup costs that must be included when measuring loading and the first request. Restoring eager linkage did not establish a decode repair and increased loading time, so that control is rejected. None of these findings establishes that a future JDK feature is required, or that every possible Java implementation must lose. [Completed linkage comparison](../../audit-artifacts/deferred-linkage-ablation-v2/github-38468048686/RESULTS.md).

**Retention and removal condition:** these candidates may enter production only after the complete runtime passes its numerical, quality, performance, startup, and resource gates. Retaining them additionally requires the bounded Java/compiler investigation defined in the proof plan. A Java replacement can remove a shim when it meets those same requirements against the retained native implementation; no JVM release date is implied.

### PTQ1_0 ternary projections

**Known:** both Java and Rust implement Bonsai's packed ternary weights with Q8 activations. Java already has SIMD arithmetic. The retained ARM source experiment found that the first native route was slower than Java SIMD; after adding NEON arithmetic, the native route delivered **2.538 times the decode throughput** and **2.610 times the prefill throughput** of Java SIMD on that host. The measured continuations agreed. These are short-prompt source experiments; final Bonsai qualification remains pending. [Bonsai evidence](../../projects/models/benchmark-results/2026-10-11-bonsai-production/README.md).

**Unresolved:** those measurements establish an implementation advantage in that experiment. They do not isolate inefficient JVM instruction generation as the cause. The review subsequently found unsupported 256-bit operations in the Java PTQ paths on a 128-bit ARM host. Replacing those operations with primitive arithmetic preserves the numerical contract and removes the measured warmed allocation while reducing first-call allocation. That repair changes the Java implementation against which Rust must be evaluated; the historical comparison cannot establish the winner against the repaired code. Packed decoding, integer accumulation, scale conversion, and scheduling still need controlled comparisons.

**Removal condition:** Java preserves activation rounding, scale rounding, accumulation order, full-model outputs, and the required performance across the affected hosts. Ternary arithmetic itself is already implemented in Java.

### CPU grouped-query attention

**Known:** Java already has vectorized attention with shared key/value reads. In the retained Granite experiment, adding Rust attention increased decode from roughly **20.5 to 25.5 tokens/second**. Both configurations already used Rust projections; this was a change to attention within that pipeline, not a comparison with an entirely Java model. [Recorded experiment](../../projects/models/benchmark-results/2026-09-15-granite-4.1-3b-alora-hybrid/preflight.md), [Java attention](../../projects/models/backend-java/src/main/java/com/integrallis/models/backend/purejava/ops/GroupedQueryAttentionKernel.java).

**Unresolved:** the historical gain does not establish a missing JVM feature or equivalence to the current Java implementation. The review found the same unsupported-width problem in Java attention scoring and softmax on a 128-bit ARM host. Splitting the logical reduction into native-width operations removes their measured warmed allocation while preserving outputs. An earlier candidate regressed x86 scoring. The corrected implementation now compiles to the same instruction and register layout as the baseline on two matched x86 hosts, and its paired timing estimate is near baseline. The strict timing confidence bound remains unresolved, so this is evidence against an ongoing execution-path regression, not a completed qualification. A current Java-versus-Rust comparison must use the corrected implementation and report both hardware results. Output equivalence also needs care: a small floating-point difference can change the selected token.

A newer matched diagnostic traced intermittent allocation in Java's weighted-attention tail to a compiler decision: HotSpot declined to inline an already compiled FMA helper, leaving vector objects to escape. Expressing the same vector FMA directly in that tail preserved every checked output and kept all eight candidate processes near 14 MB of Java allocation per request; the baseline reproduced a roughly 117 MB mode. This is a demonstrated compiler interaction with a Java source-level repair. It does not establish that Rust is necessary. Whole-model latency qualification of the repair remains pending. [Diagnostic and compiler evidence](../../audit-artifacts/q50-attention-tail-direct-screen-v1/RESULTS.md).

The current review also found that Rust attention workers construct overlapping exclusive memory views, even though their element writes target different heads. A patch confines each view to the worker's own heads. The actual attention test reproduces the memory violation under Miri on the original code and passes with the patch. Local checks also preserve outputs across 540 attention configurations and two real Granite prompt continuations, with native calls counted. The correction is committed, and the Miri check and all six supported native platform jobs have passed in [CI](https://github.com/integrallis/models/actions/runs/38277441853). Publication remains pending. This is a correctness issue to repair, independent of the performance justification. [Finding, reproduction and patch](../../projects/models-final-integration/benchmark-results/2026-10-11-gdn-proof/ATTENTION-OWNERSHIP.md).

**Removal condition:** a current comparison must preserve the required tensor and generated-output behavior across context lengths, head layouts, and shared-prefix caches, while meeting the same performance requirements.

### CUDA projections and attention

**Known:** the module exports Q4_K and Q6_K projection kernels and a grouped-query decode-attention kernel. The retained RTX 4090 experiment recorded **31.26 tokens/second against a 5.06-token/second CPU control** for the tested Granite artifact. This measures the combined accelerated route, not the contribution of each GPU kernel. Correcting missing Java-side projection dispatch produced a large gain without changing the PTX, demonstrating that an integration defect can limit GPU performance. [Decode experiment](../../projects/models/benchmark-results/2026-10-07-g4-dualpath/README.md), [separate token-parity gate](../../projects/models/benchmark-results/2026-10-07-g1-parity/README.md).

**Unresolved:** the CPU comparison is not a Rust-versus-Java comparison on the GPU. A later retained TornadoVM experiment did use the same Granite model on an RTX 4090, but recorded 36 failed device launches and never reached the exact-token gate. Its reported throughput cannot be treated as a valid measurement of working Java GPU inference. That failure supports removing the implementation we had; it does not prove that Java-authored GPU kernels cannot match the Rust implementation. Earlier Java-authored kernels accelerated a different Qwen workload, establishing feasibility on that workload only. [Failed replacement experiment](../../projects/models/benchmark-results/2026-10-07-tornado-removal/README.md), [historical Java GPU experiment](../../projects/models/models-accelerator-bench/results/vultr-a40-4q-2026-08-29.md).

**Removal condition:** a Java-authored device implementation must reproduce the projection and attention contracts and meet the same whole-model requirements on the same GPU, including compilation/startup, transfers, memory use, and fallback behavior. That requires a suitable device compiler and runtime; ordinary CPU Vector API code does not supply GPU execution. There is no established replacement date.

## Supporting code is not a separate justification for Rust

**Workers and dispatch.** The native pool schedules native compute. Vectors already has persistent Java workers, bounded polling, and stage execution. Retained experiments measured benefits from changing the Rust poll budget and from preventing Java and Rust pools from competing for cores. Those are scheduling comparisons within the combined runtime; they do not establish that an equivalent Java scheduler is inherently slower. [Scheduling measurements](../../projects/models/benchmark-results/2026-09-16-decode-gap/ANALYSIS.md), [Java executor](../../projects/vectors/vectors-core/src/main/java/com/integrallis/vectors/core/GgufPersistentRowExecutor.java).

**Batching and weight reuse.** Both implementations reuse weight blocks and activation preparation. A further Java Q8 tiling candidate was exact but slower than the existing Java implementation. That is evidence against that candidate, not against Java batching in general. [Java batching](../../projects/vectors/vectors-core/src/main/java/com/integrallis/vectors/core/PanamaVectorUtilSupport.java), [tiling experiment](../../projects/vectors/vectors-bench/jmh-results/soprano-q8-experiments-20260905.md).

**Activation preparation and half conversion.** Both sides implement these operations. Their presence inside a native projection does not establish an independent JVM limitation or a separately measured Rust advantage. They need component-level measurements where their cost matters. [Java preparation](../../projects/vectors/vectors-core/src/main/java/com/integrallis/vectors/core/GgufQuantizationSupport.java), [native implementation](../../projects/models/backend-native/src/main/rust/model-kernels/src/lib.rs).

These routines disappear when no retained native compute operation needs them. Their existence is not evidence that Java lacks workers, batching, or conversion.

## DeltaNet: a measured candidate, with unresolved release gates

**Known:** the old Rust recurrence was inactive in production, but its retained whole-model measurements reported an advantage. That made investigation necessary before deletion. The investigation found and corrected state-slot addressing when a group shrinks to one row, grouped arithmetic, and overlapping exclusive memory views. The approximate chunked implementation failed the required numerical contract and has been removed from the integration candidate. The corrected sequential implementation is staged as the default on compatible FMA hosts and supported dimensions; Java handles configurations outside that contract. None of this candidate has been published. [Investigation and retained failures](../../projects/models-final-integration/benchmark-results/2026-10-11-gdn-proof/FINAL-GDN-FINDINGS.md).

**Java alternatives were tested:** an exact Java SIMD recurrence wins the isolated kernel comparisons on the tested x86 and ARM hosts, but its whole-model decode and memory results do not preserve that advantage. The completed corrected native comparisons improve whole-request latency across the three measured model/host combinations and slightly reduce steady allocation, but still fail resident-memory and some startup or cold-request gates. Kernel speed alone cannot select the production route. The corrected whole-model harness copies every logit snapshot before another forward pass can overwrite it; earlier intermediate-logit claims from the faulty helper are invalid. [Production protocol](../../audit-artifacts/article-evidence-2026-10-13/PRODUCTION-COMPLETION-PROTOCOL.md).

**What has been fixed:** the surrounding activation implementation changed outputs between cold and warmed execution. Deterministic arithmetic removes that drift, and prebinding the native argument conversion eliminates the measured DeltaNet invocation allocation. These are implementation fixes; neither establishes that DeltaNet requires Rust. An earlier corrected runtime had a cold-allocation regression: in a separate matched x86 diagnostic, the first Bonsai request allocates about 2.12 GB against 1.18 GB with the published Vectors artifact. Profiling identifies both SwiGLU and BF16 matrix calculations as contributors. A scalar SwiGLU control reduces allocation but runs roughly three to four times slower when warm, so it is rejected. The later BF16/SwiGLU candidate reduces that first-request cost but has the remaining resource failures described above. A successful convolution component comparison cannot close a whole-model resource failure. [Current audit and retained measurements](../../library-audit-2026-10-12.md).

**Unresolved:** earlier whole-model comparisons fail resident-memory, startup, and some latency gates. Those failures remain recorded and do not establish that the Rust recurrence alone causes the extra cost. An earlier fixed-shard quality comparison fails for the smaller Qwen model: x86 scores 90 of 148 cases against 91 for the historical published-core control, and ARM scores 85 against 90. The larger model now passes its per-dataset quality comparison on both hosts. Every candidate Java/native recurrence snapshot and state check agrees. The cohorts use different process boundaries from the earlier measurements, so their scores must not be pooled. [Earlier scores, scope, and retained reports](../../audit-artifacts/2026-10-13-activation/gdn-composed-final-38362959027-complete/STATUS.md).

The controlled convolution comparison first differs at SiLU, with matching inputs, sums, history and weights. ## Removed grouped Q5_0 route

Grouped Q5_0 was excluded by production routing while still exposed by the native library. New whole-model measurements reproduce a slowdown for combined grouping; isolated groups also produce divergent greedy continuations on x86. The integration candidate removes the unused capability and dispatch support, reserves the retired capability bit, and preserves the active single-projection Q5_0 implementation. Failed experiments remain recorded. This removal has not yet been published. [Implementation and evidence](../../projects/models-final-integration/backend-native/src/main/java/com/integrallis/models/backend/nativekernel/RustGgufBatchedMatrixKernel.java).

## What authorizes retention or removal

A justified shim needs a reproducible limitation in a supported JVM, tested Java alternatives, and a measured benefit that addresses a declared workload requirement. Our evidence is not yet complete for every active route. Unknown causes remain investigation work, not promises that a future JDK will fix them.

A Java replacement must pass the numerical, task-quality, whole-model performance, startup, and resource checks before production selection changes. An inactive path with a reported gain gets an urgent performance and correctness investigation before deletion is finalized. The [build inventory and evidence validator](../../projects/models-final-integration/docs/native-shims/README.md) now reject missing, stale, or unexecuted proof records; all unresolved shim groups remain explicitly unproven. Structural checks do not establish causality. The [engineering plan](rust-shim-proof-plan.md) defines the required experiments; the [cleanup review](rust-cleanup-review.md) records the evidence and implementation status.
