## What

- Local LLM inference in Java: a GGUF file, `--add-modules jdk.incubator.vector`, no Python, no
  server, no C++ build.
- Not a wrapper around llama.cpp. **The decoders are Java.** The only native code is our own Rust
  shim kernels, and they are an optimization of that Java path, not a second implementation of it.
- **Terminology discipline for this article: do not sell "backends".** What ships in the jars is the
  Java decoder plus the Rust shims. Selectable backends — `plain-java`, `rust-ffm`, Tornado, CUDA —
  are a *measurement* device: they exist so an ablation can switch the shim off and compare, and
  they are what the harnesses drive. An article that presents "several interchangeable backends" as
  the user-facing architecture describes the benchmark rig, not the product.
- Paired with ModelJars, a catalog of **101 qualified models** out of 457 candidates, where
  "qualified" means measured on our own harness rather than claimed by a model card.
  - **101 is the union of model ids across the six qualification manifests**, and that is the only
    correct way to count it: the manifests sum to 103 because two ids are qualified on both the RAG
    and tool workloads. Counting the sum is how a wrong total gets published.
  - The largest single manifest is the RAG track, `catalog/qualifications.json` —
    `qualifiedModels: 65`, `rejectedModels: 1`, `entries: 66`,
    `policyVersion: production-rag-model-contribution-v6`, `modelsRevision: 1955b55b…`. The one
    rejected entry is `h2oai_h2o_danube3_500m_chat_gguf_q4_k_m`,
    `FAILED_MODEL_CONTRIBUTION_GATE` — a published failure, kept.
  - The second largest is embedding, `catalog/embedding-qualifications.json`, `qualifiedModels: 30`
    under a different policy entirely (`oracle-equivalence-v1`): worst-probe cosine against a
    llama.cpp oracle over 8 pinned probes, floor 0.999. **Different tracks are different gates**,
    and an article that implies one number covers all of them is wrong about the method, not just
    the count.
  - Do not confuse any of these with the 454 catalog candidates or the published marker count;
    those are different populations, and conflating them is how both "77 qualified" and "65
    qualified" got into earlier drafts.

The opener is the README's own Quick Start (`README.md:234-250`), because **the reader never names a

```java
import static org.modeljars.catalog.Qwen3_0_6b_Q4_0.MODEL;

var options = SamplingOptions.builder()
    .temperature(0.0f)
    .maxTokens(128)
    .build();

try (var runtime = ModelJars.openRuntime(MODEL)) {
    ModelPrompt prompt = runtime.chatTemplate().render(List.of(
        ChatMessage.system("Classify the user's intent in one phrase."),
        ChatMessage.user("I want to cancel my order")));
    System.out.println(runtime.model().generate(prompt, options));
}
```

the escape hatch they are, never as the headline. Naming a backend in the opening example is what
makes a reader think choosing one is their job.

- Measured, with provenance: of **65 models exercised across all three surfaces** under greedy
  sampling (shards `exercise-400/401/402/403/410/411`), **58 agree on every prompt**, 5 disagree

  (Gemma 4 E2B) genuinely differed and has since been fixed. The 5 are the subject of the open-items
  section.

## Why — the motivation, stated once and plainly

**The thesis.** A JVM application that wants a language model today has two options: call someone
else's API, or stand up a second runtime beside itself. Both are deployments. The first sends the
data somewhere; the second brings Python, a package manager, a model server, a container and an
on-call surface into a shop that already knows how to ship a jar. This library is the third option:
the model runs *in the process that asked the question*, as a dependency.

That is only worth doing if the result is honest, so the second half of the thesis is the
qualification harness. A model card is a press release. Every model offered here was measured on
our own harness, two arms on one host, and the ones that failed are recorded as failures.

- **Locality is a type, not a promise.** `RoutingDataBoundary.LOCAL_ONLY` is enforced in the
  router's candidate filter, so "this document may not leave the process" is checked by the
  compiler and the router rather than by a code review.
- **No second runtime.** One jar, one process, one deployment. No sidecar, no gRPC hop, no
  `requirements.txt`.
- **Small models are the product, not the tail.** Most requests in a real application are
  classification, extraction, routing, reranking and short answers. The catalog is ordered
  smallest-first for that reason, and the measured consequence is that **63 of 101 qualified models
  are under 1 GB** and the median is 0.85 GB.
- **Honest counterweight, stated early rather than buried.** A local 4B is not a frontier model. The
  closing section is about what to do when it falls short, which is why the router has an escape
  hatch and why the article reports escalation rate rather than hiding it.

**What this is not.** Not a wrapper around llama.cpp. **The decoders are Java.** The only native
code is our own Rust shim kernels, and they optimize that Java path rather than replacing it — which
is the whole subject of the shim section below, including when we expect to delete each one.


## The JVM as an inference host: what was impossible, what still hurts, what has to change

This is the section the rest of the article hangs on. Inference is three things in a loop — move a
few hundred megabytes of weights, multiply them by a small vector, and do it again — and the JVM
has historically been bad at exactly those three. Some of that is now fixed, which is why this
library exists at all. Some is not, which is why the Rust shims exist.

> **Label discipline for this section.** The *past* and *present* items below are each tied to code
> in this repository with a `path:line`. The *future* items are **belief, not measurement**: they
> are conditions we would need to see met, and the JDK feature names and delivery status in them
> **must be verified against the JDK's own release notes before publication**. Nothing in the future
> column is a commitment by anyone.

### Past — three things that made in-process inference impractical, and are now solved

| was | why it blocked inference | what changed |
| --- | --- | --- |
| **Calling native code was a project.** JNI meant a C toolchain, hand-written glue and a build per platform. | Any native kernel meant shipping a build system to users. | The FFM API. Our entire native seam is a `.dylib`/`.so` inside a jar plus `--enable-native-access=ALL-UNNAMED` — **no JNI, no codegen, no vendored C++**. |
| **No SIMD from Java.** You got whatever C2 chose to auto-vectorize, with no way to ask. | A scalar dot product over quantized weights is not in the same league. | The Vector API. `backend-java/build.gradle.kts:390` adds `--add-modules jdk.incubator.vector`. |
| **Off-heap tensors were capped at 2 GB.** `ByteBuffer` is `int`-indexed. | A 7B model in one mapped region was not addressable. | `MemorySegment` is `long`-indexed. Weights are held as segments and never copied to the heap — e.g. `Lfm2Weights.Matrix(MemorySegment data, GgufTensorType type, int rows, int columns)`. |

The honest summary of the past column: **this library could not have been written five years ago**,
and that is the reason it is worth writing now rather than the reason it is finished.

### Present — six live constraints, each with the code that works around it

1. **The Vector API is still an incubator module.** Every process that runs a decoder needs
   `--add-modules jdk.incubator.vector`. It is a hard dependency, not an optimization: there is no
   scalar fallback worth shipping. It appears on every test and benchmark JVM in
   `backend-java/build.gradle.kts` (`:390`, `:405`, `:719`, `:736`, `:756`, `:779`).

2. **There is no fused integer multiply-accumulate, and that is the decode loop.** A quantized GEMV
   is byte-by-byte products accumulated into wider lanes. x86 does this in one instruction; the
   Vector API cannot express it. The shim uses `_mm256_maddubs_epi16` (9 sites) and
   `_mm256_madd_epi16` (17 sites) in `backend-native/src/main/rust/model-kernels/src/lib.rs`. The
   Java side instead has to choose between three arithmetic graphs —
   `GgufQ4Kernel.{WIDENED, SHORT_PAIRWISE, UNSIGNED_PAIRWISE}` — where the latter two are documented
   as usable only "when the active vector shape supports it"
   (`vectors-core/.../GgufQ4Kernel.java`). **This single gap is the reason most of the shim exists.**

3. **Capability is discovered at runtime, not guaranteed by the platform.** vectors-core resolves a
   fifteen-field record of SIMD facts at startup — `VectorRuntimeCapabilities(providerName,
   vectorApi, configuredMaxVectorBits, preferredVectorBits, activeVectorBits, fastVectorFma,
   fastScalarFma, sve, q4ShortPairwiseSupported, q4UnsignedPairwiseSupported, …)`. A native target
   states its requirements once at compile time (`#[target_feature(enable = "avx2,fma,f16c")]`); a
   Java one asks at startup and adapts. That asymmetry is a real engineering cost, not a style
   preference.

4. **There is no half-precision type.** Every GGUF block header carries an IEEE half for the scale
   and, for the `_1` quantizations, the minimum. Java converts them with hand-written scalar bit
   arithmetic — `Float16.toFloat(short)` at
   `backend-java/.../purejava/quant/Float16.java:19`, **19 call sites** in `backend-java/src/main`
   — while the shim uses the `f16c` hardware instruction (`lib.rs:3820`, `:3937`, `:4298`). There is
   no vectorized half-to-float path in the Java code at all.

5. **Reduction order is host-dependent, and in a transformer that changes the output text.** Every
   vectorized reduction sized from `SPECIES_PREFERRED` capped by `vectors.maxBits` produced
   *different numbers on different machines*. In a retrieval score that is invisible; in a decoder it
   decides an argmax and therefore which token is emitted. `PinnedReduction` fixes the shape to eight
   lanes and writes the fold out longhand — `SPECIES = VectorSpecies.of(float.class,
   VectorShape.S_256_BIT)` and `LANES = 8` (`PinnedReduction.java:58,60`), with the rationale at
   `:22-45`: *"The width switch was the bug: it is what made the answer depend on the machine."*
   Note what this costs: on a 512-bit host we deliberately leave width on the table to buy
   reproducibility.

6. **Fine-grained dispatch is at the mercy of the scheduler.** Decode is many small jobs per token,
   each wanting the whole thread pool for a few microseconds. The shim therefore carries its own
   persistent worker pool with an explicit poll budget before parking, measured and documented in
   `lib.rs` around `DEFAULT_POLL_NANOS` — *5 ms, chosen because it is longer than any gap between
   two dispatches of one token*, with decode measured at 25.8 / 25.9 / 26.1 tok/s for 1 / 5 / 25 ms
   budgets on a dedicated-core host.

### Future — what would have to be true for each shim to be deleted

**Belief, not measurement. Verify every platform claim before publication.** Each row is written as
a falsifiable condition on *our* benchmarks, not as a prediction about anyone's roadmap:

| the shim stays until | the test that retires it |
| --- | --- |
| the Vector API exposes a widening integer multiply-accumulate (the `maddubs`/`madd` shape) | the Java quantized GEMV comes within a measured margin of the shim on the same host and shapes |
| the platform offers a half-precision type with a vectorized conversion | `Float16`'s 19 scalar call sites disappear and block-header unpacking stops showing up in a profile |
| the Vector API leaves incubation with a *stable* shape guarantee | `PinnedReduction` can use the host's full width without the answer depending on the host |
| the JVM gives a dispatch primitive with native-pool latency for microsecond jobs | the Java executor matches the persistent pool on single-token decode |

Until a row's test passes, the shim is the honest answer and the article should say so. **We have no
measurement showing any of these four conditions met today**, and the project's standing rule is that
a faster route is the only route — so each shim will be deleted on the day its test passes and not
before.


## How

- A GGUF file is a header of typed key/values plus tensors. Read the header first: it names the
  architecture, the per-layer shapes, the rope parameters and the quantization. Range-fetch it
  before implementing anything — a few MB of HTTP answers questions no fixture can.
- The decoder is a transcription of the reference graph: embed, then per layer
  norm → QKV → rope → attention → residual → FFN → residual, then the output head.
- Quantized weights are never materialised as floats. `GgufTensorType.java:33` declares
  `Q4_K(12, 256, 144)` — type id 12, 256 elements, **144 bytes per block** — and the kernel dots it
  against a Q8-quantized activation in place. (`Q5_K` 176, `Q6_K` 210, `Q8_K` 292, same file.)
- KV cache, prefix reuse and sliding windows are where throughput lives, not in the matmul.

**Header to show** — the two keys that matter for the war story, quoted from `CHANGELOG.md:12` and
`PureJavaBackendTest.java:229`:

```text
gemma4.feed_forward_length = [6144 ×15, 12288 ×20]   # per layer, not scalar
# and no expert_count key at all -> dense, with a per-layer feed-forward width
```

Hidden size 1536 is readable from the load-time error in `Gemma4ForwardPassTest.java:91`:
`"blk.15.ffn_gate.weight shape must be [1536, 6144], found [1536, 12288]"`. **Do not add other
header keys to this block without range-fetching the file** — an earlier draft invented
`embedding_length_per_layer_input` and a `block_count` line.

## The Rust shims, enumerated

The seam is narrow and versioned: an ABI integer, a platform triple, a library inside a jar, and
`--enable-native-access=ALL-UNNAMED`. It **fails closed** — a missing or mismatched library refuses
to load rather than silently running slower. There is no vendored llama.cpp and no JNI. The kernels
are ours, which is why we can fix and extend them.

The shim advertises its abilities as a capability bitmask, and Java routes per call only where a bit
is set. The authoritative list is `const CAPABILITY_*` in
`backend-native/src/main/rust/model-kernels/src/lib.rs:66-101` — **24 flags at ABI 6** — mirrored on
the Java side as `NativeKernelCapability`. Grouped by what they are for:

### 1. Quantized matrix–vector products (14 of the 24 flags)

`Q4_0`, `Q5_0`, `Q5_1`, `Q8_0`, `Q4_K`, `Q5_K`, `Q6_K`, each as a batched flag and (except `Q5_1`) a
grouped one, plus `MIXED_K_F32_GROUPED_BATCHED_MATMUL`.

- **Addresses:** present-constraint #2 — no fused widening integer multiply-accumulate in the Vector
  API, on the operation that *is* the decode loop.
- **How:** `_mm256_maddubs_epi16` / `_mm256_madd_epi16` over unpacked 4/5/6/8-bit weights against a
  Q8-quantized activation, accumulating in integer lanes and scaling once per block. Integer
  accumulation is exact and associative, which is also what lets the shim and the Java kernel agree
  **bit for bit** while splitting rows across threads.
- **Retires when:** the Vector API can express that multiply-accumulate and the Java path measures
  within margin on the same shapes.

`Q5_1` is the exception worth reading, because it shows the rule. Its per-block *minimum* needs
activation block sums that a Q8_0 activation does not carry, so the shim deliberately does **not**
invent a second arithmetic: it dequantizes the row and folds in F32 along `PinnedReduction.dot`'s
pinned order, and the parity test asserts **equality, not a tolerance**. Giving one format its own
arithmetic would have made a published vector depend on whether a host loaded the shim.

### 2. Scheduling and the worker pool (5 flags)

`PERSISTENT_WORKER_CONTEXT`, `ACTIVE_THREADS`, `POLL_BUDGET`, `MANY_GROUPED_BATCHED_MATMUL`,
`INDEPENDENT_BATCHED_MATMUL`.

- **Addresses:** present-constraint #6 — microsecond-scale jobs, hundreds per token.
- **How:** threads are created once and kept, spinning for a bounded poll budget before parking;
  active thread count is settable per context so single-token decode can ask for fewer partitions
  than batched prefill on the same pool.
- **Retires when:** a JVM dispatch primitive matches the pool's latency on single-token decode.

### 3. Weight reuse and accumulation strategy (2 flags)

`K_QUANT_BATCH_WEIGHT_REUSE`, `Q4_K_BATCH_VECTOR_ACCUMULATION`.

- **Addresses:** memory traffic rather than arithmetic — a batched prefill should unpack each weight
  block once and use it for every row in the batch.
- **How:** restructured loops that hold the unpacked block in registers across the batch.
- **Retires when:** measured as no longer a win, which is a benchmark question and not a platform
  one. **This family could in principle be done in Java today**; it is in the shim because that is
  where the loop already lived, and it is the most likely of the five to come back.

### 4. Attention (1 flag)

`GROUPED_ATTENTION_F32` — grouped-query attention for one query row across cached key/value spans.

- **Addresses:** the one part of the pass that is not a GEMV; F32 throughout, so this is about the
  shape of the loop and the pool, not about integer arithmetic.
- **Retires when:** the Java batched attention kernel matches it.

### 5. Recurrence — shipped, and deliberately not used (2 flags)

`GATED_DELTA_NET_F32`, `GROUPED_GATED_DELTA_NET_F32`.

**These two are in the ABI and Java refuses to route to them.** Both
`supportsGatedDeltaNet()` and `supportsGroupedGatedDeltaNet()` `return false` outright —
`RustGgufBatchedMatrixKernel.java:152-153` and `:195-196` — because enabling them would change the
generated bytes of models that were already certified with the Java path, invalidating pinned greedy
oracles and published tiers. An article that counted 24 capabilities as 24 active optimizations
would be wrong by two, and the reason is worth telling: **a faster path that changes output is an
epoch change, and it waits for one.**

### The honest shape of the dependency

Of the five families, exactly one — the quantized GEMV — is blocked on a platform gap we cannot close
ourselves. Two are scheduling and loop-structure work that Java could plausibly do. One is attention.
One is shipped and switched off. That is a more useful thing to tell a reader than "we have native
kernels", and it is the difference between a dependency we chose and a dependency we are stuck with.

### What 0.3.56 adds, and what it does not

**Q4_1 projections load.** Four catalogued models were refused over three tensors each. Q4_1 is a
20-byte, 32-weight block with an f16 scale and an f16 minimum and unsigned 0..15 nibbles (`q*d+m`),
not Q4_0's centred `-8` bias, and it appears for a handful of tensors inside otherwise K-quant
files — 2.5% of yi-coder's matmul weights, which was enough to refuse the whole file. Verified
against llama.cpp **token for token**, not by cosine.

The exact path is 3.3x slower at decode and 0.70x — faster — at prefill than the K-quant routes
around it. At 2.5% of weights that is roughly 6% end to end, so it is **not** the explanation for
yi-coder's throughput, which was offered as one before it was measured. A shared Q8_1 activation
path would recover the decode cost and is not in this release.

**Whisper's log-mel frontend, in `models-audio`.** Periodic Hann, Slaney mel scaling, magnitude
rather than power spectra, the dropped final STFT frame, the global `max - 8` log floor, and a DFT
with a direct path because `n_fft = 400` is not a power of two. Checked against the tensors the
artifact itself ships — `whisper-tiny-Q5_K_M.gguf` carries `frontend.window` and
`frontend.mel_filterbank` as real tensors — and agrees with both to better than 1e-6.

**This is the frontend only and it is not speech-to-text.** No encoder, no cross-attention, no
decoder, and nothing in the catalog is served by it. It ships because it is complete and verified
on its own.

### Two workloads have a corpus and no qualified model

The RAG benchmark declares ten workloads. Eight have at least one qualified model; `sql` and
`summarization` have **zero**, and both carry 12 documents and 9 cases — the same shape as every
workload that does have one. So these are closable gaps, not missing data, and the distinction
matters: a workload with no corpus is "no data" and nothing could qualify there.

For `summarization` the consequence is stated in `RagWorkload.java` itself: the router cannot select
a model for a summarization request until a qualification records that capability.

Six of the eight covered workloads have exactly one qualified model. Every one of those was closed
by a roughly 1 GB domain-tuned model rather than a large generalist — which is the smallest-first
principle showing up in the data rather than in the marketing.

Reading those two corpora also corrected an assumption worth naming: the `sql` workload does **not**
ask for SQL. Its cases ask natural-language questions *about a schema*, answered from a
one-sentence document with the required facts cited. A text-to-SQL model answers with a query,
which the grounding policy will not accept as a cited statement. The workload name describes the
subject matter, not the model class.

## Benches and Qualification

- A model card is a press release. Re-measure on one harness, and say plainly which numbers are
  *measured here*, *read in a paper*, or *believed*.
- **The two-arm rule.** A qualification is comparative: candidate plus a same-host baseline, same
  workload, same controls. One arm alone yields `NO_COMPARABLE_BASELINE`, not a verdict.
- **The gate is model contribution, not pipeline score.** `correctAnswerRate` includes an extractive
  fallback, so it scores the *pipeline*; a model that abstains throughout can still post a high one.
  Qualification gates on `modelAnswerRate` and `modelAnswerCorrectRate`.
  - The E2B evidence shows exactly this gap: `correctAnswerRate 1.0` but
    `rawCorrectAnswerRate 0.778`, `modelAnswerRate 0.778`, `extractiveFallbackRate 0.111`.
- **Library defaults are a separate gate.** Qualification runs are tuned; the smoke is not —
  `warmups 0`, `iterations 1`, `native-quantized-decode false`, and a perfect score required. That
  gate is why the bug above did not ship as a published model that throws on first use.

## Router

- The catalogue is machine-readable, so selection is a query rather than a config file.
- Five axes — cost, quality, latency, context, locality — with named policies that weight them.
  Verified constants in `RoutingPolicy.java:56-77`: `BALANCED = weights(0.30, 0.40, 0.15, 0.10, 0.05)`,
  `CHEAPEST = weights(0.70, 0.15, 0.05, 0.05, 0.05)`, `FASTEST = weights(0.05, 0.15, 0.70, 0.05, 0.05)`,
  `BEST_QUALITY = weights(0.00, 0.95, 0.00, 0.05, 0.00)`, `LOCAL_FIRST = weights(0.20, 0.30, 0.10, 0.05, 0.35)`,
  `PRIVACY_STRICT`.
- Requirements are per-request: `RoutingRequirements.Builder.requireCapability(String)`
  (`RoutingRequirements.java:65`) and `.dataBoundary(RoutingDataBoundary)` (`:74`).
- **The trap worth putting in the article.** `ModelRouter.java:298` filters on
  `candidate.capabilities().containsAll(requirements.requiredCapabilities())` — **`capabilities()`,
  not `tags()`**. A candidate built with `.tags(Set.of("rag"))` and a requirement of
  `requireCapability("rag")` matches nothing and throws `NoEligibleModelException`. A draft of this
  outline made exactly that mistake, which is a good enough reason to warn the reader.
- Every call returns its audit trail: `RoutedResult<R>(R value, RoutingDecision decision,
  List<RoutingAttempt> attempts)` (`RoutedResult.java:22`), where
  `RoutingAttempt(String modelId, Duration duration, String failureType, String failureMessage)`
  with `successful()` and `failure()` (`RoutingAttempt.java:23-36`), and
  `RoutingDecision(ModelCandidate selected, List<ModelCandidate> fallbacks, String taskType,
  double score, Map<String, Double> scoreBreakdown)` with `modelId()` and `explain()`
  (`RoutingDecision.java:35-63`).

## RAG example with the Router

**This is the payoff section. Everything else earns its place by making this work.**

A local RAG pipeline over the reader's own documents, answering locally by default, with **one**
frontier model as an escape hatch — escalation driven by evidence rather than a guess.

### The escape hatch already exists, and the tests prove it

`ModelFleetTest.java:80-97`, verbatim. The local client throws; the hosted one answers; `attempts()`
records both in order. That *is* the escape hatch:

```java
ModelFleet<Client> fleet =
    ModelFleet.<Client>builder()
        .model(candidate("local", true, 0.9, 0), failingLocal)
        .model(candidate("hosted", false, 0.8, 1), hosted)
        .policy(RoutingPolicy.CHEAPEST)
        .build();

RoutedResult<String> result =
    fleet.execute(
        RoutingRequest.builder("hello").sessionId("fallback-session").build(),
        client -> client.call("hello"));

assertThat(result.value()).isEqualTo("hosted answer");
assertThat(result.decision().selected().id()).isEqualTo("hosted");
assertThat(result.attempts())
    .extracting(RoutingAttempt::modelId)
    .containsExactly("local", "hosted");
```

### The one piece of design work: turning an abstention into an escalation

Ranked fallback fires on a **thrown exception** (`ModelInvocation.invoke(T client) throws Exception`,
`ModelInvocation.java:20-21`). But a local model falling short does **not** throw — it returns
successfully with an abstention. The real grounding API:

- `GroundedAnswerPolicy.productionDefault()` (`GroundedAnswerPolicy.java:202`), then
  `apply(String question, List<GroundingDocument> retrieved, String generatedText)` (`:249`)
  returning `GroundedAnswer(String rawText, String text, GroundingDecision decision)`
  (`GroundedAnswer.java:21`).
- `GroundingDecision` (`GroundingDecision.java:19-29`) is
  `MODEL_ANSWER`, `MODEL_ANSWER_WITH_DERIVED_CITATIONS`, `MODEL_ABSTENTION`,
  `RETRIEVAL_ABSTENTION`, `EXTRACTIVE_FALLBACK`, each carrying `modelContributed()`.
- `GroundedAnswerPolicy.ABSTENTION` is the string `"INSUFFICIENT_CONTEXT"` (`:38`).

So the escalation predicate is `!answer.decision().modelContributed()` — one accessor that already
exists, and it correctly also catches `EXTRACTIVE_FALLBACK`, the case where the pipeline papered
over the model. The bridge is to throw inside the invocation when it is true, letting the router's
existing ranked fallback do the escalation and record it in `attempts()`.

**This bridge has not been written or compiled yet.** It is the one piece of new code the article
needs, and it must exist as a real, compiling example in the repo before any of it is quoted here.
A real call site to model it on: `RagRunFactory.java:37-50`.

| --- | --- | --- |

1. A question the local model answers correctly with citations. Show latency and zero cost.
2. The same question under `RoutingDataBoundary.LOCAL_ONLY` with no eligible local model →

### The closing argument

- Report the escalation rate honestly. A measured 55% is worth more than a claimed 90%.
- Frame the frontier model as an escape hatch: one model, one trigger, one audit row. Not three
  tiers of hedging.
- Close on the asymmetry: escalation is cheap to add and expensive to use, so the engineering goal
  is to make the local path good enough that the hatch stays shut — which is exactly what
  qualification measures.

## Open items to state plainly, not bury

Verified against artifacts on 2026-10-06, except the first item, which is 2026-10-09. Provenance
named per item.

- **The harness measured a stale Rust kernel for a whole campaign, and nothing said so.**
  `backend-native`'s published JAR carries classes only — zero `META-INF/models/native` entries — so
  the `.so` comes exclusively from a separate platform JAR, and the fleet worker fetched that under
  a fixed S3 name. The object under that name was built 2026-09-28 while the Java side was 0.3.56.
  Both declare `abi=6`, so it loaded cleanly and every report recorded a consistent ABI. ABI
  compatibility is not identity, and nothing recorded the `.so` digest.
  - *Measured consequence*: one box, paired, same payload and model, two kernels, each arm twice in
    opposite order. Outputs are **identical** — same output tokens, `correctAnswerRate` and
    `modelAnswerRate` across all runs — so correctness findings stand. On the two inputs the
    relative gate actually reads, the worst case against the released kernel is decode **−0.05%**
    and end-to-end p95 **+1.76%**, and every QUALIFIED verdict has more headroom than that: the
    tightest is 1.4% above the decode floor and 3.2% below the latency ceiling. **No verdict
    changes sign, so nothing is requalified.** Evidence:
    `experiments/kernel-staleness-delta`.
  - *Not tested*: the Q5_1 half of the kernel delta. Both test models carry no Q5_1 tensors —
    `Q5_K_M` is a scheme name and does not imply Q5_1 blocks, and one was chosen on that wrong
    assumption. It does not change the conclusion only because none of the thirteen pending models
    carries Q5_1 either, verified by range-fetching all thirteen headers. Any future artifact
    carrying Q5_1 is outside what that result covers.

    the `.so` digest; a check fails if any fleet script names a measurement input literally; and
